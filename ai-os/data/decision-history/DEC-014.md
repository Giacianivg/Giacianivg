## Problema

Duas falhas ortogonais afetam a navegação no CRM em produção:

### Bug A — 3 APIs retornam 500 (backend)

| Endpoint | Dependência | Root cause |
|---|---|---|
| `GET /api/alerts/active` | `leads.alert_type`, `leads.alert_message`, `leads.alert_updated_at` | Migration **006** não aplicada no Supabase → colunas inexistentes |
| `GET /api/analytics/funnel` | tabela `conversation_states` | Migration **001** pode não ter sido aplicada no projeto Supabase atual |
| `GET /api/analytics/revenue/pipeline` | `conversation_states` + `reservations` | Mesma causa |

**Evidência:** `database/migrations/006_add_lead_alerts.sql` adiciona as colunas com `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`. O `routes/alerts.js:24` faz SELECT nessas colunas sem verificar se existem. Se a migration não foi executada → Supabase retorna erro de schema → `serverError(res, error)` → HTTP 500.

**Impacto direto:** `dashboard.html` chama as 3 rotas no carregamento. Widgets de alertas, funil e receita pipeline ficam em erro.

### Bug B — Redirect hardcoded para dashboard (frontend)

`public/auth-callback.html` linhas 126, 144, 161, 175 redirecionam **sempre** para `/dashboard.html` após auth bem-sucedida.

**Fluxo problemático:**
```
Usuário em rooms.html → token Supabase expira → requireAuth() → /login.html
    → login bem-sucedido → auth-callback.html → HARDCODED: /dashboard.html
    ← usuário perdeu o contexto, está no dashboard
```

**Impacto:** Qualquer sessão expirada em página nova (rooms, financial, map, luna-training) descarta a navegação e joga no dashboard. Usuário acredita que "a página redireciona para o dashboard".

## Opções

### Opção 1 — Fix correto em 2 frentes (RECOMENDADA)
- Aplicar migrations **006, 007, 008, 009** no Supabase de produção (SQL seguro, todas têm `IF NOT EXISTS`)
- Corrigir `auth-callback.html` para preservar parâmetro `?next=/pagina-alvo` e redirecionar para lá após login
- **Risco:** Baixo. Migrations são idempotentes. auth-callback está em `public/` (sem restrição CTO).

### Opção 2 — Fix defensivo temporário (sem acesso ao banco agora)
- Mudar as 3 rotas para retornar `{ success: true, data: {} }` quando `error` do Supabase indicar schema missing
- Corrigir `auth-callback.html` redirect
- **Risco:** Médio. Mascara o erro real. Dados continuam inexistentes no banco.

### Opção 3 — Só migrations (resolve 500s, redirect continua)
- Aplicar migrations no Supabase
- Deixar auth-callback com redirect hardcoded
- **Risco:** Baixo no banco, mas Bug B persiste.
